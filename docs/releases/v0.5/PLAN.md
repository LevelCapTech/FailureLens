# FailureLens v0.5 計画書

作成日: 2026-11-09 / 状態: 完了(結果: 基準をすべて満たし、標準にした)。結果は [REPORT.md](REPORT.md)
前の版: [v0.4 レポート](../v0.4/REPORT.md)(不採用。ただし「呼び出し関係」の加点が現行 baseline を上回ることを確認)

## このバージョンで何をするのか(やさしい説明)

FailureLens は、エラーログから「原因になっていそうなコードの場所」を順位付けして教えるツールです。

v0.4 の実験で、AI モデルを使わなくても、次の2つだけで現行の方法より良い順位が出ることがわかりました。

1. スタックトレース(エラーが起きた経路)に出てくる関数
2. その関数と「呼ぶ・呼ばれる」関係にある関数(1〜2歩先まで)

v0.5 では、これを**ライブラリ本体の baseline に取り込みます**。AI モデルは使いません(学習済みモデルは今回も使いません)。ネットワークも要らず、追加の依存もありません。

## 作るもの

| 項目 | 内容 |
|------|------|
| 新しい解析方式 | `baseline-stacktrace-callgraph`。スタックの深さと呼び出し関係で、リポジトリ全体の関数に順位を付ける |
| 現行方式 | `baseline-stacktrace-lexical` は残し、設定やコマンドの選択肢で選べる |
| 出力 | 順位・スコア・根拠。根拠には「スタックに出る関数を呼んでいる(1歩)」のように、関係を平易な言葉で書く。スコアは確率ではなく、従来どおり「ヒューリスティック」 |
| 重み | v0.4 で開発用データから選ばれた値(スタックの深さ 0.25、呼び出し関係 0.25、他は 0)をそのまま使う。今回は再調整しない |

## 標準にするかどうかの基準(実装の結果を見る前に固定)

新方式を**標準(何も指定しないときの方式)**にするのは、次の**すべて**を満たしたときだけです。1つでも満たさなければ、「選べるが標準にはしない(オプトイン)」にします。

評価データは、v0.3 の開発用データ(98ケース・4リポジトリ)です。候補は「リポジトリ全体のすべての関数」で、現行方式との比較は v0.4 と同じ約束(現行方式が返した候補を先に、残りは ID 順)で行います。

| # | 基準 | 内容 |
|---|------|------|
| 1 | 改善幅 | 関数 MRR が現行方式より **+0.10 以上**良く、対応のあるリポジトリ層別ブートストラップ(10,000回、乱数 20261030)の95%区間の**下限が 0 より大きい** |
| 2 | 偏りの確認 | リポジトリを1つ除いた4通りのどれでも、MRR の差が 0 より大きく、95%区間の下限が 0 より大きい(重みは固定なので、「設定の選び直し」ではなく「特定のリポジトリに頼っていないか」の確認) |
| 3 | 後退しない | 既存のテストがすべて通る。現行方式を選んだときの出力は従来と同じ。同梱のサンプル(`make demo`)と Gate A の1件で、新方式のファイル単位・関数単位の MRR が現行方式より下がらない |
| 4 | 速さ | 索引づけを含むケースごとの処理時間の p95 が 5 秒以下、メモリが 8 GiB 以下 |
| 5 | 表示の正直さ | 方式名が現行と区別でき、スコアはヒューリスティックのまま、根拠が平易で、文書は「測った範囲」だけを書いている |

## 結果の読み方についての注意(重要)

- 今回の評価データは、**重みを選んだ(v0.4)のと同じ開発用データ**です。つまり選択の偏りがあり、**独立した証拠ではありません**。「実際に改善した」ことの独立した確認には、新しい最終評価データが別に必要です。この版では作りません。
- v0.4 の最終評価データ(Gate C v2)は使用済みで、今回は触りません。
- したがって、この版のレポートも、「開発用データで基準を満たした/満たさなかった」とだけ書きます。「現場で優れている」とは書きません。
- 学習済みモデルは今回の経路で一切使っていません。
