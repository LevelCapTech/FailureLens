# FailureLens v0.5 評価レポート

作成日: 2026-11-09 / 計画と基準(実装前に固定): [PLAN.md](PLAN.md)

## 結論(3行)

1. v0.4 で効いた「スタックトレース+呼び出し関係」の方式を、ライブラリ本体の baseline に取り込みました(`baseline-stacktrace-callgraph`)。AI モデルは使っていません。ネットワークも追加の依存も要りません。
2. 開発用データ(98ケース・4リポジトリ)で、事前に決めた基準(改善幅・偏りの確認・後退なし・速さ・表示の正直さ)をすべて満たしたため、**この方式を標準にしました**。従来の方式(スタックトレース+語彙)は `--baseline stacktrace-lexical` で選べます。
3. ただし、**この開発用データは重みを選んだデータでもあるため、独立した証拠ではありません**。「実際の現場で改善した」とは言えません。確認には新しい最終評価データが必要です(この版では作っていません)。学習済みモデルは今回も使っていません。

## 点数の表(開発用データ、リポジトリ全体から探す条件、98ケース)

数値は高いほど良いです。MRR は「正解がどれだけ上位に出たか」(1が最高)、Top-1 は「1位が正解だった割合」です。

| 方式 | 関数 MRR | 関数 Top-1 |
|------|----------|-----------|
| 従来(スタックトレース+語彙) | 0.359 | 0.316 |
| **新(スタックトレース+呼び出し関係)** | **0.491** | 0.316 |
| 差 | **+0.132**(95%区間 +0.098 〜 +0.167) | 0.000 |

- 1位の正解率(Top-1)は変わりません。良くなったのは「正解が2位以下に出るときの順位」です。
- v0.4 の実験で選ばれた方式と比べて、98ケースすべてで順位が完全に一致しました(実装が評価した方式どおりである確認)。

### リポジトリごとの内訳(MRR)

| リポジトリ | ケース数 | 従来 | 新 |
|-----------|---------|------|----|
| boltons | 29 | 0.392 | 0.611 |
| humanize | 28 | 0.342 | 0.529 |
| sqlparse | 27 | 0.339 | 0.389 |
| jmespath | 14 | 0.363 | 0.365 |

改善は boltons と humanize で大きく、sqlparse は小さく、jmespath はほぼありません。一様に効く改善ではありません。

### 同梱のサンプルと Gate A の1件

どちらも1ケースです(一般化の根拠にはなりません)。従来方式と新方式で同じ結果でした: ファイル単位 MRR 1.0、関数単位 MRR 0.5・Top-1 0.0。後退していません。

## 何が変わったか(利用者向け)

- `FailureLens.from_baseline()` と `failurelens diagnose` の標準が、新しい方式になりました。`analysis_method` は `baseline-stacktrace-callgraph` です。
- 従来の方式は `from_baseline(strategy="stacktrace-lexical")`、または `diagnose --baseline stacktrace-lexical` で選べます。
- 出力の根拠に、新しい種類 `call_relation` が加わりました(出力スキーマを 0.1.0 から 0.2.0 に上げました。既存の項目は変わっていません)。
- スコアの値の大きさは従来と異なります(新方式の最大は 0.25)。方式をまたいでスコアを比べないでください。いずれも確率ではありません。
- パッケージのバージョン番号は変えていません。PyPI や Hugging Face への公開もしていません。

## 限界(重要)

- **独立した証拠ではありません。** 評価に使った開発用データは、v0.4 で重みを選んだデータと同じです。今回の改善幅(+0.13)は、選択の偏りを含みます。リポジトリを1つ除く確認は、この偏りをある程度見るものですが、完全には除けません。
- v0.4 の最終評価データ(Gate C v2、40ケース)では、同じ方式の MRR は 0.5955 で、現行方式に対する改善は +0.072 でした。こちらは独立した測定ですが、v0.4 の合格ライン(Top-1・MRR の改善幅)は満たしていません。今回の標準化の判断は「開発用データの基準」によるもので、v0.4 の合格ラインを満たしたという意味ではありません。
- 評価データは、小さなライブラリの1行変更を人工的に作ったものです。実際の現場の失敗に当てはまるとは限りません。
- 呼び出し関係は**名前の一致**で結んでいます。同じ名前の別の関数も結ばれることがあります(8個を超える同名は無視)。動的な呼び出しやインポートの解決はしていません。
- リポジトリが大きすぎる場合(50,000関数超)は、呼び出し関係を使わず、警告を出します。
- 今回の経路で、**学習済みモデルは一切使っていません**。公開済みの実験版モデル(v0.1)とは無関係で、その位置づけ(優位性は未確認)は変わりません。

## 次の一手(提案。実行には別途判断が必要)

1. **独立した確認**: 新しい最終評価データ(重みの選択に一切使っていないもの)で、新旧の方式を1回だけ比べる。基準の読み替えを含め、オーナーの承認が必要です。
2. **呼び出し関係の精度向上**: インポートを解決する、同名の別関数の混同を減らす、など。ただし、重みや設定を調整するときは、新しい開発用データを使うこと。
3. **学習するモデルの位置づけ**: 呼び出し関係の上に、軽い学習(位置・距離・語彙の組み合わせ)を載せるかどうかの判断。
