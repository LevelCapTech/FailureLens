# FailureLens v0.7 計画書(結果を見る前に固定)

作成日: 2026-11-10 / 状態: **固定済み(実験前)** / 前の版: [v0.6 レポート](../v0.6/REPORT.md)、[v0.5 独立確認](../v0.5/CONFIRMATION-REPORT.md)

## このバージョンで何をするのか(やさしい説明)

FailureLens は、エラーログから「原因になっていそうなコードの場所」を順位付けします。v0.5 の標準方式は、新しい評価データでも旧方式より順位が良くなりました(MRR +0.10)。しかし **「1位が正解だった割合(Top-1)」は 0.283 のまま増えず**、目標(0.4 以上)に届いていません。

v0.7 の目的は、**AI モデルを使わずに、1位の当たりを増やす手がかりを探す**ことです。考えている手がかりは次の3つです。

1. **テストのコードを後ろに回す**: エラーのスタックにはテストの関数も出ますが、原因はふつう製品側のコードです。テスト用ファイルの関数を、製品側の関数より下に置きます。
2. **製品側のスタックの関数だけを起点に「呼ぶ・呼ばれる」を数える**: テストの関数を起点にすると、無関係な関数まで近く見えてしまいます。
3. **エラーメッセージの言葉と関数名の一致**: たとえば `KeyError: 'foo'` なら、名前に `foo` を含む関数を少し上げます。

さらに、これらの手がかりの重みを小さな学習(ロジスティック回帰、順位学習)で決める候補も試します。v0.6 で、23個の手がかりを学習した候補は、一部のリポジトリで悪化しました。今回は手がかりを15個に絞って、悪化しにくいかを見ます。

## 使うデータ(Gate C は一切使わない)

| 用途 | データ |
|------|--------|
| 学習 | v0.3 の学習用データ(`train`、v0.6 と同じ手順で読み込める307件・9リポジトリ) |
| 学習内の検証 | 上のデータで、リポジトリを1つ抜く交差検証 |
| 候補の選択 | v0.3 の開発用データ(`dev`、98件・4リポジトリ)。学習には使わない |
| 最終評価 | **この版では行いません。** Gate C v3 は使用済み、Gate C v4 は別の担当が準備中で、ここでは触りません |

## 候補(6つだけ。結果を見て追加しません)

| 記号 | 内容 | 学習 |
|------|------|------|
| A | v0.5 標準方式の順位のまま、テスト用ファイルの関数を最後に回す | なし |
| B | A に加えて、「呼ぶ・呼ばれる」の起点を、製品側のスタックの関数だけにする | なし |
| C | B に加えて、エラーメッセージの言葉と関数名の一致を、固定の重み 0.15 で足す | なし |
| D | 手がかり15個のロジスティック回帰(C=0.1) | あり |
| E | 同じ手がかりの小さな決定木の集まり(参考のみ。本体に入れられる形ではないので、採用の対象にしない) | あり |
| F | 同じ手がかりの順位学習の線形モデル(C=1.0) | あり |

手がかりの具体的な定義と、学習の設定は [selection-rule.md](selection-rule.md) に固定します。

## 採用の約束(すべて満たしたときだけ採用)

比較相手は v0.5 標準方式(V5)です。「最良の候補」は、採用の対象(A, B, C, D, F)のうち、**開発用データの Top-1 が最も高いもの**(同点なら MRR、さらに同点なら学習のない候補、さらに同点なら記号順)です。

| # | 基準 | 内容 |
|---|------|------|
| R1 | 改善幅 | Top-1 が V5 より **+0.05 以上**、かつ MRR が V5 より +0.03 以上で、MRR の差の95%区間(リポジトリ層別ブートストラップ 10,000回、乱数 20261030)の下限が 0 より大きい |
| R2 | 後退しない | どのリポジトリでも、MRR が V5 より 0.05 を超えて悪くならない |
| R3 | 選び方の偏り | リポジトリを1つ除いた開発用データで最良候補を選び直しても、MRR が V5 より +0.03 以上 |
| R4 | 学習用データでの確認 | 学習用データ(リポジトリ一つ抜き)で、最良候補の MRR が V5 を上回る |
| R5 | 速さ・軽さ・オフライン | 初めて見るリポジトリ(キャッシュなし)で、索引づけを含む処理時間 p95 が 5 秒以下、メモリ 8 GiB 以下。AI モデルのダウンロードやネットワークを使わない。追加の必須依存を増やさない |

- 1つでも満たさなければ **「この方向は止める」(不採用)** です。点数を見てから基準や候補を変えません。
- 採用になった場合も、それは開発用データの結果で、独立した証拠ではありません。そのときは、候補の設定を凍結(記録)して、新しい最終評価データ(Gate C v4)で1回だけ測る準備をします。**その測定はこの版では行いません。**
- 採用になった場合の本体への取り込みは、新しい解析方式として追加し(標準は変更しません。標準にするかは最終評価の後でオーナーが判断します)、スコアは「ヒューリスティック」のままにします。

## 守ること

- 公開(Hugging Face、PyPI)、バージョン番号の変更、push はしません。
- 第三者のテストの実行はしません(すでにある失敗状態の木を使うだけ)。
- データの中身は Git にも報告書にも載せません。集計値だけです。
- 学習は小さな CPU 実験で、エポック数はありません。MLflow には、各候補の開発用・学習内の点数、選択の結果を記録します(損失曲線に当たるものはなく、その旨を明記します)。
