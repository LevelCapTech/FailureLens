# FailureLens v0.7 評価レポート

作成日: 2026-11-10 / 計画: [PLAN.md](PLAN.md) / 約束: [selection-rule.md](selection-rule.md) / 凍結: [FROZEN-CANDIDATE.md](FROZEN-CANDIDATE.md)

## 結論(3行)

1. **開発用データでは、事前に決めた5つの基準をすべて満たしました。** v0.5 の標準方式より、1位が正解の割合(Top-1)が 0.316 → 0.531(+0.214)、MRR が 0.491 → 0.619(+0.128)です。
2. 改善のほとんどは、**「テスト用ファイルの関数を後ろに回す」だけで得られます**(候補 A は Top-1 0.531、MRR 0.617)。選ばれた候補 D(15個の手がかりを学習した重み付け)は、A より MRR が 0.002 高いだけで、実質的に同じです。
3. これは**開発用データでの結果で、独立した証拠ではありません**。そこで、候補を凍結して(新しい解析方式 `stacktrace-callgraph-weighted` として、標準にはせず追加)、新しい最終評価データ(Gate C v4)で**1回だけ**測る準備をしました。その測定はこの版では行っていません。標準は v0.5 のままです。

## 何を試したか

Gate C v3 の結果(MRR は上がったが Top-1 は上がらない)を受けて、**AI モデルを使わずに**1位の当たりを増やす手がかりを探しました。開発用データの分析から、**候補になる関数の約52%がテスト用ファイルの関数**で、原因はテストの外(製品側のコード)にあることがわかっていたためです(テスト用ファイルかどうかは、ファイルパスだけで決めます)。

| 候補 | 内容 | 学習 |
|---|---|---|
| A | v0.5 の順位のまま、テスト用ファイルの関数を最後に回す | なし |
| B | A + 「呼ぶ・呼ばれる」の起点を製品側のスタックの関数だけにする | なし |
| C | B + エラーメッセージの言葉と関数名の一致を足す | なし |
| D | 15個の手がかりのロジスティック回帰 | あり(1回) |
| E | 同じ手がかりの小さな決定木の集まり(参考のみ) | あり(1回) |
| F | 同じ手がかりの順位学習の線形モデル | あり(1回) |

学習用データは v0.3 の学習用(307件・9リポジトリ)、選ぶデータは v0.3 の開発用(98件・4リポジトリ)です。Gate C のデータには一切触れていません。

## 点数(開発用データ、98ケース、リポジトリ全体から探す条件)

MRR は「正解がどれだけ上位に出たか」(1が最高)、Top-1 は「1位が正解だった割合」です。

|---|---|---|---|---|---|
| **v0.5 標準方式(v5)** | 0.491 | 0.316 | 基準 | 基準 | 0.548 |
| A | 0.617 | 0.531 | +0.126(+0.090〜+0.164) | +0.214(+0.143〜+0.286) | 0.632 |
| B | 0.381 | 0.316 | -0.110(-0.146〜-0.075) | 0.000 | 0.486 |
| C | 0.367 | 0.276 | -0.124(-0.165〜-0.085) | -0.041 | 0.485 |
| **D(選ばれた)** | **0.619** | **0.531** | **+0.128(+0.089〜+0.167)** | **+0.214(+0.143〜+0.286)** | 0.623 |
| E(参考) | 0.603 | 0.531 | +0.112(+0.070〜+0.154) | +0.214(+0.143〜+0.286) | 0.634 |

- 選び方の約束(Top-1 → MRR → 学習なし優先)では、A・D・E が Top-1 で同点になり、MRR が最も高い **D が選ばれました**。D と A の MRR の差は 0.002 で、誤差の範囲です。

## 分かったこと(うまくいかなかった候補も含めて)

- **効いたのは「テストのコードを後ろに回す」ことです。** 候補の半分以上がテスト用ファイルの関数なので、これを下げるだけで1位の当たりが大きく増えます。
- **B と C は逆効果でした(不採用)。** 「呼ぶ・呼ばれる」の起点を製品側のスタックの関数だけにすると、MRR が大きく下がりました。原因の関数は、テストの関数から**直接呼ばれている**ことが多く、テストのフレームも「呼び出し関係の起点」として大事だったためです。仮説が外れました。
- **学習の効果は小さいです。** 学習した D・E・F は、学習なしの A と比べて、上乗せがほとんどありません(F は A より悪い)。

## 限界(重要)

- **「原因は製品側のコードにある」という前提が評価データに入っています。** 評価データは、小さなライブラリの製品側の関数を1か所変更して作った合成データなので、原因が必ず製品側にあります。**実際の現場の失敗で、原因がテスト用の補助コードやフィクスチャにある場合は、この方式は悪化します。** 「テスト用ファイルの判定」はパスだけで決めており、完全ではありません。
- 結果は開発用データ(98件・4リポジトリ)での選択で、独立した証拠ではありません。改善はリポジトリにより大きく異なります。
- 学習は1回で、乱数のばらつきは見ていません(D のロジスティック回帰は乱数に依存しません)。
- 本体への取り込み(`stacktrace-callgraph-weighted`)の出力が、評価用の実装と全ケースで一致することを確認しました(98/98)。
- Gate C v3 は使用済みで、今回も見ていません。
