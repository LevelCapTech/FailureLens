# FailureLens v0.4 計画書

作成日: 2026-11-07 / 状態: 計画(結果はまだありません)
前の版: [v0.2 レポート](../v0.2/REPORT.md)(不採用)、[v0.3 レポート](../v0.3/REPORT.md)(不採用)

## なぜ方向を変えるのか(やさしい説明)

v0.2 と v0.3 は、「ログに出てくる関数の中から、原因を並べ替える」モデルでした。ふつうの方法(語彙の一致)もほぼ同じ情報を使うため、学習データを増やしても差がつきませんでした。

さらに、新しい最終評価データでは、原因の関数がスタックトレースに出ないケースが 45%(18/40)あります。ログに出ない関数は、並べ替えでは見つけられません。

v0.4 では、次の2つを試します。

- **A. リポジトリ全体から探す**: ログに出ない関数も含め、リポジトリのすべての関数を候補にして順位を付ける。
- **B. 呼び出し関係を使う**: スタックトレースに出る関数を起点に、「それを呼ぶ関数」「それに呼ばれる関数」を近いものとして加点する。症状の場所と原因の場所が離れた失敗に効く見込みがあります。

## 評価条件の読み替え(オーナー承認済み、数値は変えない)

凍結基準の数値(Top-1 0.4、MRR 0.6 など)はそのままにし、**候補の範囲だけ**を「ログに出る関数」から「リポジトリ全体の関数」に変えます。

| 方法 | 内容 |
|------|------|
| 同梱 baseline | 現行の製品(スタックトレース+語彙)。出力は現行どおり |
| 語彙の一致(全体) | リポジトリ全体の関数を、エラーログとの語彙の一致だけで順位付け |
| v0.4 の方法 | リポジトリ全体を、モデルの類似度+呼び出し関係+スタックの深さで順位付け |

## 進め方と「止める」基準(結果を見る前に固定)

| 段階 | 内容 |
|------|------|
| 1 | 全体から探す評価の仕組みを作る(開発用データ98件、4リポジトリで使う)。**追加の学習はしない** |
| 2 | 既存の v0.1・v0.2-b・基盤モデルそのままを、全体から探す条件で測る。呼び出し関係の加点を、開発用データで少数の設定から選ぶ(選び方は事前に固定) |
| 3 | 「止める」判定(下記) |
| 4 | 通った場合のみ、選んだ1設定を新しい最終評価データ(Gate C v2、40件)で**1回だけ**測る |
| 5 | レポート作成、MLflow に記録 |

**止める基準(開発用データ)**: 全体から探す条件で、最良の方法の関数 MRR が「語彙の一致(全体)」を **+0.05 以上** 上回り、かつ対応のあるブートストラップの95%区間の下限が0より大きいこと。満たさなければこの方向は止め、Gate C v2 は使わずに温存し、「この規模のモデルでは語彙の一致で十分」という結論も含めて報告します。

## 合格ライン(変更しない)

Gate B の凍結基準を、候補の範囲だけ読み替えて、字義どおり当てはめます。

- 関数 Top-1 が 0.4 以上、MRR が 0.6 以上
- 比較相手からの改善が Top-1 で +0.4 以上、MRR で +0.1 以上
- 30件以上、3リポジトリ以上
- 推論 p95 が 5 秒以下(リポジトリ全体の索引づけを含む)、メモリ 8 GiB 以下、10億パラメータ以下

判定: 全部満たしても、公開・配布は人間のオーナーの判断です。満たさなければ不採用で、公開しません。

## 守ること

- データの中身は Git にも報告書にも載せません。集計値だけです。
- 外部リポジトリのテスト実行は、ネットワークを切った Docker の中だけです。
- 新しい最終評価データは、選んだ1設定につき1回だけ使います。
- 結果は MLflow に記録します。Discord の通知は使いません。
- 不採用の版は公開しません。
