# FailureLens v0.4 評価レポート

作成日: 2026-11-09 / 計画: [PLAN.md](PLAN.md) / 方法と選び方(実験前に固定): [selection.md](selection.md)

## 結論(3行)

1. 「リポジトリ全体から原因を探す」条件で、開発用データ(98ケース)では、選んだ方法が語彙の一致を大きく上回りました(MRR 0.49 対 0.19)。事前に決めた「止める基準」は満たしたので、新しい最終評価データ(Gate C v2、40ケース)で1回だけ測りました。
2. 最終評価では、Top-1 は 0.50 で基準(0.4 以上)を満たしましたが、**MRR は 0.5955 で基準 0.6 にわずかに届かず**、現行の baseline に対する改善幅の基準(Top-1 +0.4、MRR +0.1)も満たしませんでした。**v0.4 は「不採用」です。** 公開はしません。
3. 効いた要素は**学習済みモデルではありませんでした**。選ばれた設定は、モデルの類似度を使わず、「スタックトレースの深さ」と「関数どうしの呼び出し関係」だけを使っています。モデル単独の順位付けは、語彙の一致より悪い結果でした。

## 点数の表

数値は高いほど良いです。Top-1 は「1位が正解だった割合」、MRR は「正解がどれだけ上位に出たか」(1が最高)です。候補の範囲は、どちらも「リポジトリ全体のすべての関数」です。正解の関数は、全体の候補に常に含まれていました(含有率 1.0)。

## 不採用の理由

- MRR が基準にわずかに届かず、現行 baseline に対する改善幅の基準を満たしませんでした。
- 改善の中身が、「モデル」ではなく「呼び出し関係のヒューリスティック」です。FailureLens の学習済みモデルが価値を出せることは、今回も示せませんでした。

## 何がわかったか

1. **モデル単独の順位付けは、このタスクに向いていません。** 「エラーログ」と「関数のソース」の類似度で全体から探すと、基盤モデルも v0.1 も v0.2 も、語彙の一致より悪い結果でした(MRR 0.04〜0.06)。関数のテキストそのものを問い合わせにすると、12ケースすべてで1位に出るので、仕組みの不具合ではありません。ログの文章と、1行だけ壊れた関数の間に、類似度で拾える手がかりが乏しいためと考えられます。
2. **効いたのは呼び出し関係です。** スタックトレースに出る関数から、呼び出しで1〜2歩の関数に加点するだけで、現行 baseline より良くなりました(開発用 MRR 0.359 → 0.491、最終評価 0.524 → 0.596)。最終評価の改善は、区間が0を含まず、偶然とは考えにくいです。ただし、基準の求める幅(+0.1)には届きません。
3. この加点は、モデルもネットワークも要らず、ライブラリの依存を増やさずに実装できます。現行 baseline の拡張として検討する価値があります。ただし、今回はライブラリの出力を一切変えていません。

## 限界

- 評価データは、人工的に1行を壊したデータで、4つの小さなライブラリから作っています。実際の現場の失敗に当てはまるとは限りません。
- 最終評価データは、選んだ1設定につき1回だけ使いました。再測定はしていません。
- 設定の選択は開発用データで行いました(324通り)。選択の偏りは、リポジトリ1つを除く確認で見ましたが、完全には除けません。
- 「現行 baseline」の全体候補での順位は、baseline が返した候補を先に、残りを ID 順に置く約束で作っています。
- 学習は一切していません。追加のモデル学習で状況が変わるかは、今回は検証していません。
- 推論時間は、モデルを使わない設定の値です。モデルを使う場合は、全関数の埋め込みで開発用データで、キャッシュのない状態の最初のケースが最大で約130秒かかりました。

## 次の一手(提案。実行には別途判断が必要)

1. **呼び出し関係の加点を、モデルなしの改善として評価し直す**: 現行 baseline との差を、より大きく、実際に近いデータで確認する。基準を満たす見込みがあるか、オーナーが判断する。
2. **学習済みモデルの位置づけを見直す**: 2回続けて、モデルが語彙の一致を超えられませんでした。モデルを使う方向を続けるか、「モデルなしのツール」として整えるかの判断が必要です。
3. **MRR 0.6 の基準**: 今回は 0.0045 の差です。基準は変えません(変更はオーナーの承認が必要)。
