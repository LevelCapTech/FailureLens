# FailureLens v0.2 計画書

作成日: 2026-11-07 / 状態: 完了(結果: 不採用)。結果は [REPORT.md](REPORT.md)、候補の選定は [selection.md](selection.md) を参照。

## このバージョンで何をするのか(やさしい説明)

FailureLens は、プログラムが失敗したときのエラーログから「原因になっていそうなコードの場所」を順位付けして教えるツールです。

現在公開している実験版(v0.1)は、**学習に使った例がわずか12件**で、「ふつうの方法(baseline)より本当に良いか」を**まだ誰も測っていません**。v0.2 では次の3つをやります。

1. **きちんと測る**: 学習に一切使っていないリポジトリで、baseline と新モデルを同じ条件で比べます。
2. **学習データを増やして作り直す**: 例を十数倍に増やし、複数の候補モデルを作ります。
3. **結果が悪くても隠さない**: 事前に決めた合格ラインに届かなければ「不採用」とし、理由を書きます。

## 用語

| 用語 | 意味 |
|------|------|
| baseline | 機械学習を使わない、スタックトレースと単語の一致で順位付けする現行の方法 |
| 学習データ | モデルに覚えさせる例 |
| 開発用評価データ(dev) | 候補モデルの比較・選択に使う評価データ。学習には使わない |
| 最終評価データ(Gate C) | 最後に1回だけ使う評価データ。学習にも選択にも使わない |
| Top-1 | 1位の候補が正解だった割合(高いほど良い) |
| MRR | 正解が何位に出たかの平均的な良さ。1に近いほど良い |
| train損失 / validation損失 | 学習用データ/確認用データでの誤差。小さいほど良い |
| 過学習 | 学習データだけに合わせすぎて、新しいデータでは悪くなること。train損失は下がるのにvalidation損失が下がらない/上がるときに疑う |

## 合格ライン(結果を見る前に固定。変更しない)

2026-10-29 に凍結済みの Gate B 基準をそのまま使います。最終評価(Gate C)の結果で機械的に判定します。

| 項目 | 合格ライン |
|------|-----------|
| 関数レベル Top-1 | 0.4 以上 |
| 関数レベル MRR | 0.6 以上 |
| baseline からの改善 | Top-1 が +0.4 以上、MRR が +0.1 以上 |
| 評価ケース数 | 30件以上、3リポジトリ以上 |
| 推論時間 | p95 が 5秒以下 |
| 使用メモリ | 8 GiB 以下 |
| モデルサイズ | 10億パラメータ以下 |

判定ルール:
- すべて満たせば **採用候補**。それでも公開・配布・採用の判断は人間のオーナーが行います。
- 1つでも満たさなければ **不採用**。v0.1 は「実験版・優位性未確認」のままです。
- 開発用評価(dev)は候補の選択だけに使い、合否の根拠にはしません。最終評価は選んだ1候補につき1回だけです。

## 進め方

| 段階 | 内容 | 状態 |
|------|------|------|
| 0 | 記録基盤: 学習中の通知、MLflow への記録(損失・過学習の指標・学習率・epoch数・評価点数)とモデル登録 | 完了 |
| 1 | 現行モデル(v0.1相当)と baseline を、最終評価データで1回測る(基準点) | 完了 |
| 2 | 権利の確認できたリポジトリから、学習用・開発用データを増やす | 完了 |
| 3 | 複数の設定(学習率・epoch数など)で候補モデルを学習。dev で比較して1つ選ぶ | 完了 |
| 4 | 選んだ候補を最終評価(1回)。合格ラインで採否判定 | 完了 |
| 5 | `REPORT.md` を作成。MLflow に全バージョンを比較できる形で残す | 完了 |

## 守ること

- 学習・評価データの中身(ケース、ラベル、ソース、ケース別の結果)は Git にも報告書にも載せません。載せるのは集計値だけです。
- 重みは Git に入れず、手元の MLflow にだけ保存します。
- Hugging Face への新しい公開、PyPI リリースは、この計画に含みません。
- 点数を作ったり、良く見せるために基準を変えたりしません。
