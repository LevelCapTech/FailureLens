# FailureLens v0.2 評価レポート

作成日: 2026-11-07 / 計画: [PLAN.md](PLAN.md) / 候補の選定: [selection.md](selection.md)

## 結論(3行)

1. 学習データを12件から178件に増やして候補モデルを3つ作り、開発用データで最良の候補 **b** を選びました。
2. その b を、学習にも選択にも使っていない最終評価データ(30ケース・3リポジトリ)で1回だけ測りました。
3. **事前に決めた合格ラインには届きませんでした。v0.2 は「不採用」です。** b は現行 v0.1 よりわずかに良い点数でしたが、ふつうの方法(語彙の一致)に**勝ったとは言えない**差でした。公開済みの v0.1 実験版も「優位性は未確認」のままです。

## 点数の表(最終評価データ、30ケース)

数値は高いほど良いです。Top-1 は「1位が正解だった割合」、MRR は「正解がどれだけ上位に出たか」(1が最高)です。

### A. 現行の公開製品の検索(baseline)との比較

| 方法 | Top-1 | MRR |
|------|-------|-----|
| baseline | 0.033 | 0.033 |
| v0.2 候補 b | 0.033 | 0.033 |

どちらも30件中29件で、そもそも候補を1つも見つけられませんでした。最終評価データのエラーログが書いているファイル名が、実際のソースにないためです。この比較では**どのモデルも同じ点数**になり、順位付けの良し悪しは測れていません。合格ラインは機械的にすべて未達です。

### B. 補助的な比較(候補をあらかじめ与え、語彙の一致で順位付けする方法と比べる)

| 方法 | 関数 Top-1 | 関数 MRR | ファイル Top-1 |
|------|-----------|----------|----------------|
| 語彙の一致(比較対象) | 0.400 | 0.700 | 0.933 |
| v0.1(現行の実験版) | 0.467 | 0.733 | 0.967 |
| **v0.2 候補 b** | **0.533** | **0.767** | **0.967** |
| b と語彙の一致との差 | +0.133 | +0.067 | |
| 差の95%区間 | -0.10 〜 +0.37 | -0.05 〜 +0.18 | |

差の区間が0をまたぐのは、「偶然の範囲かもしれない」という意味です。30ケースと少ないため、この差から「良くなった」とは言い切れません。

## 合格ラインとの照合(事前に固定した基準)

| 項目 | 合格ライン | 結果 | 判定 |
|------|-----------|------|------|
| 関数 Top-1 | 0.4 以上 | 0.533(補助比較) / 0.033(baseline比較) | baseline比較では未達 |
| 関数 MRR | 0.6 以上 | 0.767(補助比較) / 0.033(baseline比較) | baseline比較では未達 |
| Top-1 の改善幅 | +0.4 以上 | +0.133(補助) / 0.0(baseline) | **未達** |
| MRR の改善幅 | +0.1 以上 | +0.067(補助) / 0.0(baseline) | **未達** |
| ケース数・リポジトリ数 | 30件・3個以上 | 30件・3個 | 達成 |
| 推論時間 p95 | 5秒以下 | 0.69秒以下 | 達成 |
| 使用メモリ | 8 GiB 以下 | 2.7 GiB 以下 | 達成 |
| モデルサイズ | 10億以下 | 約1.37億 | 達成 |

速さ・軽さ・大きさは基準内です。**精度の改善幅**が足りませんでした。

## 不採用の理由

- 改善幅の合格ライン(Top-1 +0.4、MRR +0.1)に、大きく届いていません。
- 点数の差が小さく、偶然との区別がつきません。
- 今回の最終評価データでは、同梱の baseline が候補を出せず、公平な順位付けの比較ができませんでした。評価の作り方に限界があります。

## 何がわかったか

- データを増やすと、確認用データでの損失は下がりました(v0.1 の約0.72 → 約0.37)。過学習の警告は出ていません。
- ただし、損失が下がっても、順位付けの点数はほとんど伸びませんでした。今回の「単一行の変更を見つける」合成データでは、語彙の一致でも高い点数が出るためと考えられます。
- 学習データの量より、**「語彙の一致では解けない」難しい例**が足りない可能性があります。

## 限界

- 評価は30ケース・3リポジトリで、人工的に作った(1行を壊した)データです。実際の現場の失敗に当てはまるとは限りません。
- 各候補の学習は1回で、乱数によるばらつきは見ていません。
- 開発用評価では、同梱の baseline との比較ができませんでした(同名関数の扱いで評価コードが候補を拒否したため)。
- 学習データは、テストで検出できた変更だけが残る作り方で、よくテストされたコードに偏ります。

## 次の一手(提案。実行には別途判断が必要)

1. **難しい例を増やす**: 複数行の変更、原因と症状の場所が離れた失敗、語彙の手がかりが少ない例を作る。
2. **最終評価データの改善**: ログに実在するパスが入るように作り直し、同梱の baseline と公平に比べられる形にする。人間のオーナーの承認が必要です。
3. **公開について**: v0.2 は不採用のため、Hugging Face への新しい公開はしません。公開済み v0.1 の説明は「優位性は未確認」のままです。
