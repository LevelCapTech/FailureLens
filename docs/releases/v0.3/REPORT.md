# FailureLens v0.3 評価レポート

作成日: 2026-11-07 / 計画: [PLAN.md](PLAN.md) / 候補の選び方と結果: [selection-rule.md](selection-rule.md)、[selection.md](selection.md)

## 結論(3行)

1. 「難しい例」を増やして、候補モデルを6つ作りました(学習データは 351 件、v0.2 の約2倍)。
2. 開発用データ(98ケース)で、**過学習していない候補は、ふつうの方法(語彙の一致)にも v0.2 の最良候補にも負けました**。
3. 事前に決めたルールにより、**v0.3 は「不採用」**です。最終評価データ(Gate C v2)は使っていません(次の版のために温存)。公開もしません。

## 何をしたか

| 項目 | 内容 |
|------|------|
| 新しい最終評価データ(Gate C v2) | 40ケース・4リポジトリ。ログのパスが実在し、同梱 baseline も動く形。**未使用**(次の版まで温存) |
| 学習データ | 351 件(10 リポジトリ)。半数以上が「難しい例」(複数行の変更、引数の取り違え、原因と症状の関数が違う失敗など) |
| 開発用データ | 98 件(4 リポジトリ)。58%が難しい例 |
| 候補 | a〜d(あらかじめ計画した4つ)+ 過学習のため追加した e, f |

## 点数(開発用データ、98ケース)

数値は高いほど良いです。Top-1 は「1位が正解だった割合」、MRR は「正解の順位の良さ」(1が最高)です。

| 方法 | 関数 Top-1 | 関数 MRR | 結果 |
|------|-----------|----------|------|
| 語彙の一致 | 0.592 | 0.776 | 比較対象 |
| v0.1(公開中) | 0.439 | 0.684 | 悪い |
| v0.2 の最良候補 | 0.551 | 0.753 | 参考 |
| v0.3 候補 e(過学習なしで最良) | 0.531 | 0.743 | **不採用** |
| v0.3 候補 f | 0.520 | 0.741 | 不採用 |
| v0.3 候補 a〜d | 0.58〜0.61 | 0.774〜0.787 | 過学習のため失格(参考) |

差の95%区間は、e の MRR 差(語彙の一致との比較)が -0.104〜+0.039 で、0をまたぎます。「同等かやや悪い」と読むのが妥当です。

## 合格ラインとの照合

最終評価(Gate C v2)を実施していないため、合格ラインの判定は行っていません。**実施しなかった理由は、dev の段階で採用の条件(語彙の一致と v0.2 の最良候補を上回ること)を満たす候補がなかったためです。**

| 項目 | 合格ライン | 結果 |
|------|-----------|------|
| 関数 Top-1 / MRR / 改善幅 | 0.4 以上 / 0.6 以上 / +0.4・+0.1 以上 | **未測定**(最終評価を実施せず) |
| 推論時間・メモリ・サイズ | 5秒以下・8 GiB 以下・10億以下 | 未測定(参考: モデルは約1.37億パラメータ) |

## なぜ不採用か

- 過学習していない候補(e, f)は、語彙の一致より低い点数でした。
- 学習を長くした候補(a〜d)は、点数は語彙の一致と同程度ですが、確認用データでの損失が途中から悪化しました(過学習)。ルールどおり除外しています。
- 難しい例を増やしても、「語彙の一致では解けない問題で、モデルが勝つ」状態には届いていません。

## 何がわかったか

- このモデル(基盤モデルの最後の層だけを学習する方法)では、数百件規模の合成データでは、語彙の一致を超える効果が出にくい可能性が高いです。
- 学習データを増やすほど過学習が早く出ます(確認用データの損失が最良になるのは 1〜5 epoch 目)。データの量だけでなく、**種類の多様さ**が足りません。
- 失格にした候補 a, b の点数は語彙の一致と同程度でした。ルールを後から変えて救済することはしていません。

## 限界

- 評価は人工的に作った(コードの一部を壊した)データです。実際の現場の失敗に当てはまるとは限りません。
- 各候補の学習は1回で、乱数のばらつきは見ていません。
- 学習・確認用の入力は 1536 トークンに切っています(メモリの都合。評価時は切りません)。
- dev での推論時間は、他の処理が同時に動いていたため速度の根拠になりません。

## 次の一手(提案。実行には別途判断が必要)

1. **別の学習方法を試す**: 最後の層だけでなく、より多くの層や別の学習目的(順位を直接学習する方式など)を比べる。
2. **学習データの多様化**: リポジトリの種類、失敗の種類、実在のバグ修正履歴など、人工変更以外の例を増やす(権利確認が必要)。
3. **「語彙の一致」に勝てない領域での使いどころの見直し**: たとえば、ファイル単位の絞り込みでは既にほぼ満点であり、関数単位での追加価値があるかを検討する。
4. 最終評価データ(Gate C v2)は未使用のまま残してあります。採用候補が出たときに1回だけ使います。
