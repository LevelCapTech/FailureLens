# FailureLens v0.3 計画書

作成日: 2026-11-07 / 状態: 完了(結果: 不採用)。結果は [REPORT.md](REPORT.md)、候補の選定は [selection.md](selection.md) を参照。
前の版の結果: [v0.2 レポート](../v0.2/REPORT.md)(不採用)

## なぜ作るのか(やさしい説明)

v0.2 でわかった問題は2つです。

1. **評価が公平でなかった**: 最終評価データのエラーログに、実在しないファイル名が書かれていました。そのため、現行の baseline が候補を見つけられず、「新モデルが baseline より良いか」を測れませんでした。
2. **学習の例が簡単すぎた**: 「1行だけ壊す」例は、単語の一致だけでも解けます。モデルを使う意味が出る、難しい例が足りません。

v0.3 では、この2つを直します。

## 作ること

| 段階 | 内容 |
|------|------|
| 1 | (完了)**新しい最終評価データ(Gate C v2)**: 学習・開発用・旧最終評価のどれとも重ならない、権利確認済みのリポジトリで作る。エラーログのパスが実在し、baseline も公平に動く形にする |
| 2 | **難しい例を増やした学習データ**: 複数行の変更、原因と症状の場所が離れた失敗、語彙の手がかりが少ない例を追加する |
| 3 | 複数の候補を学習し、開発用データで1つ選ぶ(選ぶルールは学習の前に固定) |
| 4 | 選んだ候補を新しい最終評価データで1回だけ測り、合格ラインで採否を判定 |
| 5 | (完了)`REPORT.md` を作成し、MLflow に全版を記録 |

## 合格ライン(変更しない)

v0.2 と同じ、2026-10-29 に凍結済みの Gate B 基準です。

- 関数 Top-1 が 0.4 以上、MRR が 0.6 以上
- baseline からの改善が Top-1 で +0.4 以上、MRR で +0.1 以上(同梱の baseline との同条件比較)
- 30件以上、3リポジトリ以上
- 推論 p95 が 5 秒以下、メモリが 8 GiB 以下、10億パラメータ以下

判定ルール:
- 新しい最終評価データは、**どの候補についても、選んだ1候補につき1回だけ**使います。旧最終評価データ(v0.2 で結果を見たもの)は、選択に使いません。
- 全部満たしても、公開・配布は人間のオーナーの判断です。満たさなければ不採用で、公開しません。

## 守ること

- データの中身(ケース、ラベル、ソース、ケース別結果)は Git にも報告書にも載せません。
- 外部リポジトリのテスト実行は、ネットワークを切った Docker の中だけで行います。
- 学習・評価の結果は MLflow に記録します。Discord への通知は使いません(ローカルの記録のみ)。
- 不採用の版は公開しません。

## 評価データの上限に関する注意(結果を見る前に追記、2026-11-07)

新しい最終評価データ(40ケース・4リポジトリ)では、同梱の baseline の検索が正解の関数を候補に入れられるのは 40件中22件(0.55)です。残りの18件は、正解の関数がスタックトレースに出ないため、現行の検索では見つけられません。

そのため、「現行の検索の候補を並べ替える」方式のモデルは、この評価データで MRR が 0.55 を超えられません(凍結基準の MRR 0.6 に届かない)。これはモデルの出来とは関係のない、評価の仕組みの上限です。

扱い方(基準は変更しません):
- 最終評価では、次の2つの結果を**両方**報告します。判定は、凍結基準を字義どおり当てはめた結果に従います。
  1. 同梱の baseline の候補を並べ替える条件(上限 0.55 がある)
  2. 候補をあらかじめ全部与える条件(上限なし。相手は語彙の一致)
- 上限のために基準に届かなかった場合は、そのとおりに「不採用」と書き、上限が原因であることも併記します。
- 基準そのものを変える(たとえば検索も含めたモデル)判断は、人間のオーナーの承認が必要です。承認なしに変更しません。
