# FailureLens v0.6 評価レポート

作成日: 2026-11-09 / 計画: [PLAN.md](PLAN.md) / 選び方の約束: [selection-rule.md](selection-rule.md)

## 結論(3行)

1. 小さな学習(ロジスティック回帰、順位学習、小さな決定木)で、スタックと呼び出し関係などの手がかりの重みを自動で決めると、**開発用データでは v0.5 の標準方式より MRR が約 +0.08〜+0.09 良くなりました**(偶然とは言いにくい差)。
2. ただし、**事前に決めた約束(選び方の約束)の基準を、最良の候補は満たせませんでした。** 最良の候補は AI モデルの類似度を使うもので、**初めて見るリポジトリでは埋め込みの計算に最大約 150 秒かかり**、処理時間の基準(5 秒以下)を超えたためです。
3. したがって **v0.6 は「この方向は止める(不合格)」** です。最終評価(Gate C v3)には進みません。凍結した候補も残していません。AI モデルを使わない候補は速いのですが、一部のリポジトリで v0.5 より悪化し、基準を満たしませんでした。

## 何を試したか

v0.5 の標準方式は、「スタックの深さ」と「呼び出し関係」に人間が決めた固定の重み(0.25 と 0.25)を付けて順位を付けていました。v0.6 では、次の23個の手がかり(AI モデルを使うときはさらに2個)から、重みや組み合わせを**学習で決める**候補を6種類、作りました。

- スタックでの位置(最も内側か、何番目か)
- 呼び出し関係の向き(呼ばれているか、呼んでいるか)と距離
- ログの単語との一致
- 関数名やファイルの場所がログと似ているか
- 関数の大きさ など

| 候補 | 手法 | 手がかり |
|------|------|----------|
| A | ロジスティック回帰(C=1.0) | 手がかり23個 |
| B | ロジスティック回帰(C=0.1) | 手がかり23個 |
| C | 順位学習の線形モデル | 手がかり23個 |
| D | 小さな決定木の集まり | 手がかり23個 |
| E | 小さな決定木の集まり | 手がかり23個 + AI モデルの類似度 |
| F | ロジスティック回帰 | 手がかり23個 + AI モデルの類似度 |

学習データは v0.3 の学習用データ、選ぶためのデータは v0.3 の開発用データ(98件・4リポジトリ)です。最終評価データ(Gate C)には一切触れていません。

## 点数(開発用データ、98ケース、リポジトリ全体から探す条件)

数値は高いほど良いです。MRR は「正解がどれだけ上位に出たか」(1が最高)、Top-1 は「1位が正解だった割合」です。

| 方法 | 関数 MRR | 関数 Top-1 | v5 との MRR の差(95% 区間) |
|------|----------|-----------|------------------------------|
| 語彙の一致(全体) | 0.187 | 0.092 | - |
| 旧方式(スタック+語彙) | 0.359 | 0.316 | - |
| **v0.5 標準方式(今の製品)** | **0.491** | 0.316 | 基準 |
| 候補 A | 0.570 | 0.469 | +0.079(+0.031〜+0.126) |
| 候補 B | 0.570 | 0.469 | +0.078(+0.033〜+0.123) |
| 候補 C | 0.484 | 0.357 | -0.007(-0.058〜+0.045) |
| 候補 D | 0.571 | 0.490 | +0.080(+0.028〜+0.131) |
| **候補 E(最良)** | **0.586** | **0.510** | **+0.095(+0.048〜+0.143)** |
| 候補 F | 0.581 | 0.490 | +0.090(+0.046〜+0.134) |

- 選び方のルールどおり、開発用データの MRR が最も高い**候補 E**が「最良の候補」になりました。
- AI モデルを使わない最良の候補は D(MRR 0.571)で、E との差は 0.015 でした。AI モデルの類似度は、わずかに役に立ちました。
- v5 を再現する確認(v0.5 のレポートと同じ MRR 0.4913)も取れています。

## 基準との照合(最良の候補 E)

| 基準 | 内容 | 結果 | 判定 |
|------|------|------|------|
| R1 改善幅 | v5 より +0.03 以上、区間の下限が 0 より大きい | +0.095(下限 +0.048) | 達成 |
| R2 後退しない | どのリポジトリでも v5 より 0.05 を超えて悪くならない | 最も悪いリポジトリで -0.046 | 達成(ぎりぎり) |
| R3 選び方の偏り | リポジトリを1つ除いて選んでも +0.03 以上 | +0.069 | 達成 |
| R4 学習データ内の確認 | 学習データ内の一つ抜き検証で v5 を上回る | 0.632 対 0.548(+0.084) | 達成 |
| R5 速さと軽さ | 処理時間 p95 が 5 秒以下、メモリ 8 GiB 以下 | p95 **150.7 秒**、メモリ 1.88 GiB | **未達** |

**1つでも満たさなければ「この方向は止める」**と事前に決めていたので、結果は不合格です。

### なぜ処理時間が長いのか

AI モデルの類似度を使うには、リポジトリのすべての関数をモデルに通して数値(ベクトル)にする必要があります。一度計算すれば保存できますが、**初めて見るリポジトリでは、その計算が丸ごと必要**です。開発用データの4リポジトリでの初回の計算時間は、13 秒(humanize)、18 秒(jmespath)、51 秒(sqlparse)、150 秒(boltons)でした(CPU のみ)。約束では「キャッシュなしの代表値」を処理時間に含めると決めていたので、最も遅い boltons が p95 を決めました。

「保存した後は速い」という使い方なら基準を満たせたかもしれませんが、それは**約束にない読み替え**なので、基準は変えていません。

## 確かめたこと(信頼性)

- **学習データの扱い:** 学習用データ 351 件のうち 44 件(すべて idna)は、製品の索引の大きさの制限(1ファイル 300 KB)を超える失敗状態の木になるため、評価の仕組みで読み込めず、学習から外れました。学習には 307 件・9 リポジトリを使いました。
- **正解の含まれ方:** 候補の範囲(リポジトリ全体)に正解の関数が含まれる割合は、開発用・学習用ともに 100% です。
- **安全面:** ネットワークを使わず、外部のテスト実行もしていません。データの中身は Git にも報告書にも載せていません。
- **記録:** MLflow に、6候補と選定の結果(合計7つの実行)を記録しました(`v0.6.0-candidate-a`〜`f`、`v0.6.0-selection`)。重みのない小さな実験のため、損失の曲線やエポック数はありません(代わりに、開発用データの点数と学習内の一つ抜き検証の点数を記録しています)。

## 限界

- 結果は、開発用データ(98件・4リポジトリ)での選択です。候補が6つだけなので選択による偏りは小さいですが、**独立した証拠ではありません**。独立した確認は、新しい最終評価データでの1回だけの測定が必要です(この版では行いません)。
- 各候補の学習は1回で、乱数によるばらつきは見ていません(決定木には乱数の影響があり得ます)。
- 評価データは、小さなライブラリの1行変更を合成したものです。現場の失敗に当てはまるとは限りません。
- 処理時間は CPU のみ・同時に別の処理が動いている状態での測定です。

## 次の一手(提案。実行には別途判断が必要)

1. **埋め込みの費用を下げる**: 初回の計算を減らす(小さなモデルにする、関数の本文の長さを制限する、必要な関数だけを計算する)。これで R5 を満たせるなら、同じ約束で再評価できます。
2. **リポジトリ間のばらつきを調べる**: sqlparse で悪化する理由を調べ、手がかりを足す(たとえば関数の大きさの正規化、メソッドと関数の区別)。
3. **v5 を標準のまま維持する**: 現行の製品(v0.5)は、固定の重みで全体を底上げする方式のまま、リポジトリ間のばらつきが小さい現状を維持するのも合理的です。
4. **新しい最終評価データで独立に確かめる**: 準備中の Gate C v3 が出来た後に、**D や E のような候補を事前に固定したうえで**1回だけ測る案もあります。ただし、今回の約束では「凍結しない」と決めたので、約束を変える判断が必要です。
